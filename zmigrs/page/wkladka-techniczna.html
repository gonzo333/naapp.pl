1. Wprowadzenie i zakres dokumentu

Niniejszy dokument stanowi specyfikację techniczną do oferty na wykonanie i wdrożenie strony internetowej dla Stowarzyszenia Związek Miast i Gmin Regionu Świętokrzyskiego (ZMiGRS). Opisuje zastosowaną architekturę, stos technologiczny, model bezpieczeństwa oraz przyjęte standardy jakości i dostępności.

Dokument przeznaczony jest dla osób decyzyjnych oraz specjalistów IT po stronie Zamawiającego i obejmuje zarówno warstwę frontendową (interfejs użytkownika), jak i integrację z systemem bazodanowym oraz usługami zewnętrznymi.

2. Architektura systemu

2.1 Model ogólny

Serwis internetowy oparty jest na architekturze Jamstack (static-first SPA – Single Page Application). Podejście to polega na oddzieleniu warstwy prezentacji (HTML/CSS/JavaScript) od warstwy danych (REST API), co przynosi wymierne korzyści w zakresie bezpieczeństwa, wydajności i utrzymania.

Kluczowa cecha architektury: brak serwera aplikacyjnego po stronie frontendu. Strona internetowa to zbiór statycznych plików serwowanych przez serwer HTTP – nie ma możliwości ataku na interpreter, bazy danych czy logikę serwerową poprzez interfejs użytkownika.

2.3 Nawigacja i routing

Serwis realizuje nawigację po stronie klienta (client-side routing) bez przeładowań strony. Funkcja showPage() zarządza widocznością sekcji DOM, co eliminuje zbędne żądania HTTP i zapewnia natychmiastowe przejścia między zakładkami. Wszystkie zasoby niezbędne do wyświetlenia każdej sekcji są wczytywane przy pierwszym otwarciu strony.

3.3 Integracja z Oracle APEX REST API (ORDS)

Dane dynamiczne (aktualności, uchwały, sprawozdania, załączniki) pobierane są asynchronicznie z REST API opartego na Oracle REST Data Services (ORDS), wchodzącego w skład platformy Oracle APEX. Komunikacja odbywa się wyłącznie metodą GET za pośrednictwem protokołu HTTPS z szyfrowanym połączeniem TLS.

Obsługiwane endpointy REST:

  • /api/articles – lista aktualności
  • /api/article/{id} – pełna treść artykułu
  • /api/resolutions – lista uchwał
  • /api/reports – lista sprawozdań
  • /api/attachments/{type}/{id} – wykaz załączników do pozycji
  • /api/attachments/{type}/file/{fileId} – pobranie pliku

4. Bezpieczeństwo

4.1 Brak serwerowej powierzchni ataku po stronie frontendu

Strona internetowa składa się wyłącznie ze statycznych plików (HTML, CSS, JS, grafiki). Na serwerze WWW nie działa żaden interpreter skryptów serwerowych (PHP, Python, Node.js itp.), baza danych ani silnik szablonów. W związku z tym wyeliminowane są całe klasy podatności, m.in.:

  • SQL Injection (brak warstwy serwerowej z dostępem do bazy danych od strony frontendu)
  • Remote Code Execution przez interpretator serwerowy
  • Server-Side Request Forgery (SSRF)
  • Ataki na sesję serwerową (brak cookies sesyjnych / mechanizmu logowania publicznego)

4.2 Komunikacja sieciowa – HTTPS / TLS

Całość komunikacji między przeglądarką użytkownika a serwisem oraz serwisem a zewnętrznymi API odbywa się wyłącznie z użyciem protokołu HTTPS (TLS 1.2 / TLS 1.3). Zapewnia to:

  • Poufność danych w transmisji (szyfrowanie end-to-end)
  • Integralność przesyłanych treści (ochrona przed modyfikacją w ruchu)
  • Uwierzytelnienie serwera (certyfikat SSL/TLS)

4.3 Ochrona przed Cross-Site Scripting (XSS)

W miejscach, gdzie treści z API są wstawiane do DOM (aktualności, uchwały, sprawozdania), stosowane są bezpieczne metody przypisania właściwości elementów DOM (element.textContent, element.title, atrybuty danych) zamiast bezpośredniego wstawiania surowego HTML. Tam gdzie wymagane jest użycie innerHTML (np. treść artykułu pobrana z zaufanego API), dane pochodzą z kontrolowanego backendu Oracle APEX.

4.4 Zarządzanie załącznikami i plikami

Pliki do pobrania (uchwały, sprawozdania, dokumenty statutowe) są przechowywane po stronie backendu lub w dedykowanej usłudze chmurowej Google Drive. Strona internetowa nie obsługuje przesyłania plików przez użytkowników – brak możliwości wykonania ataku typu malicious file upload.

4.5 Polityka żądań zewnętrznych (referrer policy)

Osadzona mapa Google Maps posiada ustawiony atrybut referrerpolicy="no-referrer-when-downgrade" zgodnie z rekomendacją W3C, ograniczając zakres informacji o URL przekazywanych do zewnętrznych usług.

4.6 Brak persistencji danych po stronie klienta

Aplikacja nie korzysta z localStorage, sessionStorage, IndexedDB ani plików cookies do przechowywania danych użytkownika. Brak mechanizmu logowania dla użytkowników publicznych eliminuje ryzyko kradzieży sesji (session hijacking).

Podsumowanie profilu ryzyka: zastosowana architektura static-first SPA z REST API w modelu tylko-do-odczytu (read-only dla użytkowników publicznych) minimalizuje powierzchnię ataku do minimum możliwego dla serwisu internetowego prezentującego informacje publiczne.

5. Wydajność i optymalizacja

5.1 Ładowanie zasobów

Strona ładuje się jako pojedynczy dokument HTML. Brak konieczności wczytywania ciężkich frameworków JavaScript (plik script.js obsługuje całą logikę aplikacji). Czas do pierwszej interakcji (Time to Interactive) jest zatem bardzo krótki.

  • Obrazy w galeriach ładowane z atrybutem loading="lazy" (natywne lazy loading)
  • PhotoSwipe ładowany dynamicznie jako moduł ES (import on demand) – tylko gdy użytkownik otwiera artykuł z galerią
  • Czcionki systemowe – zero zewnętrznych żądań do serwerów czcionek
  • Brak pakietyzacji npm/webpack – brak bloatware zależności

5.2 Sieć CDN dla zasobów zewnętrznych

Biblioteka PhotoSwipe serwowana jest z sieci CDN jsDelivr – jednej z największych i najbardziej wydajnych sieci dystrybucji treści open-source, z węzłami w Polsce i po całej Europie. Zapewnia to niskie opóźnienia i wysoką dostępność bez obciążania własnego serwera.

5.3 Responsywność (RWD)

Interfejs jest w pełni responsywny i dostosowany do wszystkich rozdzielczości ekranu:

Breakpoint Układ
Desktop (≥ 1024px) Siatka 3-kolumnowa, nawigacja pozioma, mapa 500px
Tablet (768px – 1024px) Siatka 2-kolumnowa dla zarządu
Mobile (< 768px) Układ jednkolumnowy, nawigacja 2×4, mapa 350px

Wdrożone media queries CSS zapewniają poprawne działanie na urządzeniach mobilnych, tabletach i komputerach stacjonarnych bez konieczności instalowania dedykowanych aplikacji mobilnych.

6. Dostępność (Accessibility)

Projekt uwzględnia wytyczne WCAG 2.1 (Web Content Accessibility Guidelines) na poziomie AA:

  • Obrazy posiadają atrybuty alt z opisami tekstowymi
  • Elementy interaktywne (przyciski, linki) posiadają atrybuty title
  • Struktura nagłówkowa (h1–h4) jest hierarchiczna i semantyczna
  • Kontrast kolorów tekstu na tle spełnia wymagania WCAG 2.1 AA (stosunek ≥ 4,5:1)
  • Strona jest operowalna za pomocą klawiatury (focus management na elementach nawigacji)
  • Formularz kontaktowy posiada etykiety <label> powiązane z polami
  • Język dokumentu zadeklarowany jako lang="pl" (wsparcie czytników ekranu)

7.1 System załączników

Uchwały i sprawozdania obsługują dynamiczne pobieranie załączników poprzez modal okienkowy. System odpytuje API o listę plików powiązanych z daną pozycją i prezentuje użytkownikowi nazwę, datę oraz przycisk pobrania dla każdego pliku. Pobieranie odbywa się poprzez przekierowanie do bezpośredniego URL zasobu – bez buforowania pliku w przeglądarce i bez ekspozycji tokenów autoryzacyjnych po stronie klienta.

7.2 Panel administracyjny

Do zarządzania treścią (artykuły, uchwały, sprawozdania) dostarczony zostanie dedykowany panel (add_edit_article.html) umożliwiający dodawanie i edycję wpisów bez ingerencji w kod źródłowy strony. Panel komunikuje się z tym samym Oracle APEX REST API z rozszerzonymi uprawnieniami zapisu.

8. Kompatybilność z przeglądarkami

Serwis korzysta wyłącznie z natywnych API przeglądarek dostępnych bez polyfilli w każdej nowoczesnej przeglądarce. Minimalne wspierane wersje:

Przeglądarka Minimalna wersja

Zastosowanie ES Modules (natywne) oraz CSS Grid/Flexbox (powszechne wsparcie od 2018) gwarantuje poprawne działanie na ponad 98% urządzeń używanych przez polskich internautów według danych StatCounter (2024).

9. Utrzymanie i aktualizacje

9.1 Niski koszt utrzymania

Brak zależności od frameworków JavaScript oraz menedżera pakietów (npm) oznacza brak konieczności regularnego aktualizowania dziesiątek pakietów. Jedyna biblioteka zewnętrzna (PhotoSwipe) jest dostarczana w pinned wersji z CDN i nie wymaga ingerencji w kod przy braku znanych podatności.

9.2 Aktualizacja treści

Treści dynamiczne (aktualności, uchwały, sprawozdania) zarządzane są wyłącznie przez panel administracyjny zintegrowany z bazą Oracle APEX – bez potrzeby dostępu do kodu źródłowego strony. Treści statyczne (władze, członkowie, statut) wymagają jednokrotnej interwencji programistycznej przy zmianie stanu faktycznego (np. zmiana składu zarządu po wyborach).

9.3 Monitoring i dostępność

Dostępność serwisu zależy od dostępności serwera WWW (hostingu) oraz Oracle APEX API. Zalecane jest wdrożenie monitoringu HTTP (np. UptimeRobot lub Pingdom) z alertami e-mail/SMS dla administratorów. Statyczna warstwa frontendowa jest odporna na awarie backendu – użytkownik zobaczy stronę z komunikatem o braku danych zamiast błędu serwera.
